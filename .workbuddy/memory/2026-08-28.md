## 关键根因修正：contextIsolation 下 dataTransfer 整体为空（20:25）
实测拖放仍提示「未能读取拖入的文件路径」。`contextIsolation: true` 时 Electron 会**整体清空**渲染进程 `dataTransfer`（不仅是 `File.path`，`files` 列表与 `text/uri-list` 也为空）——这是安全设计，渲染进程根本读不到本地路径。之前 `onDragOver` 已 preventDefault、遮罩能显示，但 drop 时 dataTransfer 为空。
正确方案：走主进程 `webContents.on('drop-files', (event, files) => { event.preventDefault(); webContents.send('app:files-dropped', files) })`，files 是完整路径数组（含文件夹），不受 contextIsolation 影响。
- `main/index.ts`：`createWindow` 里给 `window.webContents` 注册 `drop-files`（类型缺失，用 `as unknown as { on: ... }` 断言绕过）。
- `shared/types.ts`：`DesktopApi.onFilesDropped(cb) => unsub`。
- `preload/index.ts`：`ipcRenderer.on('app:files-dropped', ...)` 桥接。
- `renderer/src/main.tsx`：预览 mock 加 `onFilesDropped: () => () => {}`。
- `App.tsx`：`pageRef` 跟踪当前页；`useEffect` 注册 `onFilesDropped`，page==='upload' 调 `addItemsFromPaths(files)`，`page==='browse'` 调 `setOssDroppedPaths(files)`。`UploadPage`/`BrowsePage` 的 `onDrop` 改为只 `preventDefault`+重置遮罩（不再读路径）；`BrowsePage` 新增 `droppedPaths`/`onDroppedConsumed` props 与 `useEffect` 消费（校验 profile/bucket 后 `uploadToCurrentDir` 立即上传）。删除了失效的 `getDroppedPaths`。

## 再次修复：页面 preventDefault 抑制了 drop-files（20:35）
上一步以为根因只是 dataTransfer 被清空，改用主进程 drop-files。但实测仍失败——**真正的阻断点**：渲染进程在 `window`/页面的 `dragover`、`dragenter` 上调用 `preventDefault`，会让 Electron 判定"拖放已被页面接管"，于是**不再 emit 主进程的 `drop-files` 事件**，路径永远收不到。
- 删除 App 全局 `window.addEventListener('dragover', preventDefault)`（只保留 `drop` 兜底防导航）。
- 删除 `UploadPage`/`BrowsePage` 的 `onDragOver` 与 `onDragEnter` 里的 `preventDefault`（仅保留用于显示遮罩与深度计数）。
- 保留 `onDrop` 的 `preventDefault` 作为 DOM 导航兜底。
- 各层加 console.log 诊断：`[main] drop-files`、`[preload] app:files-dropped`、`[renderer] onFilesDropped`、`[renderer] BrowsePage 收到 droppedPaths`，以及 preload 顶层 DOM drop 诊断（观察 dataTransfer.files 是否为空）。

教训：Electron 中只要页面 preventDefault 了 dragover/dragenter，主进程 drop-files 就不触发；本地路径只能从 drop-files 拿。

## 真正根因与最终修复（20:55）
之前我把 `dragover` 的 `preventDefault` 删掉了，导致鼠标显示 not-allowed（圆圈斜杠）。那其实是**Chromium 在告诉你「这里不接受放置」**。直觉上这应该不影响 OS 层的 drop-files，但实测下来**它确实会同时阻断 drop-files**——Electron 的 `drop-files` 触发依赖渲染侧确认了放置目标。

最终结论：dragover 上 **必须** `event.preventDefault()` + `event.dataTransfer.dropEffect = 'copy'`。这同时解决：
1. 鼠标光标变成「copy +」正常图标
2. Chromium / Electron 把这次放置识别为合法，触发 drop-files
3. 渲染侧 `drop` 事件也能正常 preventDefault，避免导航

具体改动：
- `UploadPage.handleDragOver` 与 `BrowsePage.handleBrowseDragOver`：补回 `event.preventDefault()`，配合 `dropEffect='copy'`、`effectAllowed='copy'`。
- 删除 `styles.css` 里之前为绕过 not-allowed 光标加的 `cursor: copy !important`（preventDefault 已让 Chromium 自动切光标，CSS hack 不再需要）。
- 各层日志保留（方便再有问题时定位）。

教训（修正前次错误结论）：
- Chromium / Electron 拖放：**dragover 不 preventDefault → 整个放置链路被阻断**，包括主进程 drop-files。
- `dataTransfer.dropEffect` 只是「光标样式」，阻止默认行为靠 `preventDefault`。

## 终极根因：webContents 根本没有 drop-files 事件（21:00）
图标修好但仍无反应。查 `node_modules/electron/electron.d.ts`（Electron 33.4.11）发现：
- `drop-files` 只存在于 **`Tray`** 接口，且标注 `@platform darwin`（仅 macOS）。
- `WebContents` 区间内 `drop-files` 出现 **0 次** —— `webContents.on('drop-files', ...)` 是**不存在的事件**，注册后永远不触发（之前靠 `as unknown as` 类型断言才骗过 tsc，掩盖了问题）。此前整套「主进程 drop-files → IPC 转发」链路全是死代码。

**正确方案：Electron 32+ 用 `webUtils.getPathForFile(file)`**
`File.path` 已在 Electron 32 移除，官方替代是 `webUtils.getPathForFile(File): string`，且**只能在预加载（隔离上下文）里调用**。

最终链路（已删除全部 IPC 中转）：
- `preload/index.ts`：`import { contextBridge, ipcRenderer, webUtils } from 'electron'`；`getPathsForFiles: (files) => files.map(f => webUtils.getPathForFile(f)).filter(Boolean)`（含 try/catch 兜底）。
- `shared/types.ts`：`getPathsForFiles: (files: File[]) => string[]`（替换 `onFilesDropped`）。
- `App.tsx`：`UploadPage.handleDrop` / `BrowsePage.handleBrowseDrop` 里直接
  `window.desktopApi.getPathsForFiles(Array.from(event.dataTransfer.files))` 同步拿路径，再 `collectFromPaths` 展开上传。
- 删除：`main/index.ts` 的 `drop-files` 监听与 `console.log`；`App.tsx` 的 `pageRef`、`ossDroppedPaths`、`onFilesDropped` useEffect、`BrowsePage` 的 `droppedPaths`/`onDroppedConsumed` props；`preload` 的诊断 `document.addEventListener('drop')`。
- `UploadPage` 恢复 `onDropPaths` prop → App 传 `addItemsFromPaths`。
- `main.tsx` 预览 mock 同步改 `getPathsForFiles`。

关键教训：
1. **Electron 事件名要查 `electron.d.ts` 确认归属对象与 `@platform`**，不要凭印象；用 `as unknown as` 绕过类型报错时，往往是 API 根本不存在。
2. Electron 32+ 拖放取路径：renderer 拿 `File` → contextBridge 传给 preload → `webUtils.getPathForFile()`。
3. dragover 仍需 `preventDefault()` + `dropEffect='copy'`（光标 + 触发 drop）。

## 批量操作（删除/复制/移动/下载/重命名）加进度反馈（21:54）
用户反馈删除时「一直卡着、无法操作、不知道删完没」。根因：主进程 `for` 循环逐个 `await client.delete/copy`，文件夹展开后可能上千次网络往返；渲染层 `setBusyOp(true)` 后零反馈。

### 新增通用进度通道 `oss:op-progress`
- `shared/types.ts`：`OpProgressEvent { done, total, current?, failed? }`；`DesktopApi.onOpProgress`。
- `preload/index.ts`：桥接 `oss:op-progress`。
- 约定：`total === 0` 表示**扫描阶段**（`current` 放提示文案如「正在扫描对象… 已发现 N 个」）。

### 主进程（main/index.ts）
- `expandObjectKeys` 加可选 `onScan(scanned)` 回调，每页 list 后上报扫描数。
- **删除改批量**：新增 `DELETE_BATCH_SIZE = 100`，用 `client.deleteMulti(batch)` 分批删（OSS 上限 1000），上千次往返压到几十次；整批失败时退化逐个删除并累计 `failed`；返回 `{ deleted, failed }`。
- 复制/移动：先展开全部 source→target pairs（边展开边上报扫描），再逐个 copy(+delete) 并上报 `done/total/failed/current`；返回 `{ count, failed }`。
- 下载、重命名：同样逐个上报；下载失败的单个文件不再中断整批。

### 关键坑：`deleteMulti` 的 quiet 模式
`ali-oss/lib/common/object/deleteMulti.js` 里 `deleted` 取自响应 XML 的 `<Deleted>` 节点（**成功**项）。
`quiet: true` 时 OSS 只返回失败的 `<Error>`、不返回 `<Deleted>` → `deleted` 恒为空数组 → 会被误判成整批失败。
**所以绝不能传 `quiet: true`**。已写进 `src/shared/ali-oss.d.ts` 的注释。
- `ali-oss.d.ts` 的 `OSSClient` 补了 `deleteMulti` 声明（项目自建类型文件）。

### 渲染层（App.tsx）
- 新增 `opProgress` / `opLabel` state、`beginOp(label)` 辅助、`useEffect` 订阅 `onOpProgress`。
- 新增 `OpProgressBar` 组件（1053 行）：扫描阶段显示提示文案，处理阶段显示「删除中 3/10（失败 1）」+ 当前文件名 + 进度条；有失败时进度条转红。
- 放置位置：浏览页 notice 上方（`busyOp || downloading` 时）、删除确认弹窗、复制/移动弹窗、重命名弹窗。删除按钮在 busyOp 时文案变「删除中…」。

## 修复：切换页面导致 OSS 上传队列丢失（22:20）
用户反馈：在 OSS 文件页加入文件后不点开始上传，切到「上传中心 / 设置」再切回，上传进度里的任务全没了。

**根因**：App 用条件渲染切换页面
```jsx
page === 'upload' ? <UploadPage/> : page === 'browse' ? <BrowsePage/> : <SettingsPage/>
```
切到别的页时 `BrowsePage` 被**卸载**，它内部的 `uploadQueue` / `uploadPendingRef` / `uploading` 三个 state 全部销毁，切回来自然为空。

**修复**：把这 3 个 state 提升到 App 层（与上传中心的 `tasks` 保持一致），通过 props 传入 BrowsePage。
- App 层新增（33-35 行）：`browseUploadQueue` / `browseUploadPendingRef` / `browseUploading`。
- `BrowsePage` 签名新增 5 个 props：`uploadQueue`、`setUploadQueue`、`uploadPendingRef`、`uploading`、`setUploading`。
- `setUploadQueue` 类型写成 `UploadTask[] | ((queue: UploadTask[]) => UploadTask[])`，因为 `clearAllUploads` 里是直接传 `[]`。
- BrowsePage 内所有上传函数（`enqueueToCurrentDir` / `runBrowseUpload` / `clearAllUploads` …）代码未动，自动指向 App 层 state。

**额外收益**：后台上传中切走页面，async 函数继续跑且更新的仍是 App 层 state；切回来能看到真实进度，`uploading` 也不会错误地重置为 false（之前会）。

`uploadOpen`（弹窗开关）仍留在 BrowsePage 内——切页关闭弹窗是合理行为；顶部上传图标上的 badge 会提示队列中还有 waiting/uploading 任务，点击即可重新打开。

教训：Electron/React 应用中，凡是「切页仍要保留」的状态（上传队列、进度）都应放在页面容器（App）层，而不是页面组件内部；页面组件用条件渲染时会被卸载。
